# Customer experience and security — review release

Implementation branch: `feat/customer-security-tracking`, based on production `512a76c`. Audit was written before application changes in `CUSTOMER_SECURITY_AUDIT.md`. No push to main, deployment, production migration, configuration change or real verification email is performed by this work.

## Behavior

- `/track-order` reuses the existing secure tracking provider, guest capabilities, server abuse limits, ownership checks and the full OrderHistoryPage. The floating control is now a shortcut. New confirmation/guest emails use `/track-order#track=...`; old `/orders#track=...` links retain the captured capability and redirect to the dedicated route. Plain `/orders` remains available. Guest responses still contain only status and fulfilment method.
- Customer status is active, suspended, deactivated or deleted. Lifecycle actions require a Super Admin, an 8–500 character reason and typed action/customer confirmation. Changes and audit records commit together. Every change increments the existing session_version; suspension/deactivation/deletion also set is_active false, clear push tokens and invalidate recovery/verification tokens. Existing guest capabilities for that customer's orders are revoked when present.
- Delete is a permanent, non-login tombstone. The unique email is retained as a protected historical identity reservation, names/phones/address profile data are cleared, and password is randomized. Orders, items, payments, invoices and delivery records are not deleted or cascaded. Retention is intentional, not a claim of complete erasure. An unfinished order or pending/approved refund blocks deletion, including soft-deleted unfinished orders. Reactivation of a deleted account is denied. Operator retention policy review is required before deployment.
- Customer listing now supports server-side search, status/verification filters and pagination. Unpaginated calls retain the existing contract for manual-order selectors. The management page no longer infers account records from a partial orders list. Details expose authorized profile/address/recent order data, never password hashes.
- All registration aliases use the active registration handler. New customers are always marked verification-required and receive a Resend verification email. Login remains possible for verification/recovery; unverified required accounts cannot place customer orders or access private email-owned order details. Tokens use 32 cryptographically random bytes, SHA-256 hashes at rest, email binding, 30-minute expiry and single-use consumption under row locks. Resends invalidate older tokens and use per-user/per-peer shared database limits. Confirmation errors do not echo tokens; email errors log types only. URLs use fragments, cleared from the browser address bar.
- Existing accounts are not marked verified without evidence. Migration gives legacy accounts an explicit grace state. `CUSTOMER_EMAIL_VERIFICATION_REQUIRED=true` ends that grace period for every customer. Publish a deadline and a `/verify-email` self-service link through the existing CMS/customer communications before cutover. This flag must be enabled before declaring mandatory verification complete for legacy accounts.
- Checkout offers connected Create Account / Log In routes with an allowlisted return target. Cart storage is unchanged. A delivery draft stays only in tab JS memory across SPA auth steps; it is cleared on successful checkout/logout and is not persisted as sensitive browser storage. Reloading the tab may lose the delivery draft while the persisted cart remains. Verification state refreshes on returning focus. Duplicate clicks are guarded in the UI; a customer-scoped idempotency key reuses the existing unique key column, with a request hash preventing changed-payload replays. New orders populate customer_user_id. Customer account checks and deletion share a user-row lock before order creation/inventory deduction. Existing stock/delivery/payment rules are retained.

## Explicit additive migration

Live connection follow-up: Socket.IO now uses database-backed account/session checks, authorizes order subscriptions, prunes revoked recipients before emissions, and disconnects the customer's sockets on account actions. It reuses the existing server/event loop and requires no new broker. New orders use customer_user_id for ownership; email-only fallback remains limited to legacy unlinked orders. Manual-order creation takes the same customer lock and rejects inactive linked accounts, while administrative manual orders do not require a customer's email-verification step.

Deletion retains address rows referenced by historical orders (and hides them from the deleted profile), preserving financial/delivery references. Unreferenced saved addresses and current profile/contact display fields are removed/cleared. This is controlled retention, not complete erasure.

Script: `backend/scripts/migrate_customer_security.py`. With no arguments it prints a plan. Review the target database and take a backup before running:

```
python backend/scripts/migrate_customer_security.py --apply
```

It adds users.account_status, account_status_reason, account_deleted_at, email_verified_at and email_verification_required; orders.checkout_request_hash; and the email_verification_tokens/account_action_limits tables. It reuses existing users.session_version and orders.manual_idempotency_key. It is repeatable, preserves existing statuses, initializes inactive legacy users as deactivated, and never bulk-verifies accounts. New ORM columns require this migration before deploying the new backend; startup schema mutation is not a substitute. The existing guest tracking migration/configuration remains a prerequisite for guest capability features.

## Rollback

Do not restore the baseline Socket.IO signature-only/order-room behavior. Keep the new live-account/ownership checks in a reviewed compatibility backend, or temporarily disable `/socket.io` while rolling back. REST session revocation alone does not secure the older WebSocket implementation.

Pause checkout before rollback to prevent pending idempotent submissions being retried against older code without idempotency enforcement. Prefer a forward fix for verification/security issues. If restoring the prior app release, retain all additive tables/columns, account tombstones, is_active/session_version revocations, audit logs and historical transactions. Do not drop tokens/columns or restore deleted customer profiles from an old database snapshot as an application rollback. Old code respects is_active/session_version but does not enforce the new verification policy; keep checkout paused or deploy a reviewed compatibility gate until verification enforcement is restored. Keep compatibility redirects for new `/track-order` email links when rolling back the frontend, preserving fragment privacy. End-to-end restore/lock behavior must be rehearsed on PostgreSQL staging. No destructive schema rollback is supplied.
