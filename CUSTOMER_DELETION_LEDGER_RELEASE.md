# Customer deletion and retained order ledger

Private receipt evidence is now implemented on this branch; RETAINED_RECEIPTS_RELEASE.md supersedes the earlier attestation-only receipt instructions below. Durable checksum-verified copies, authenticated viewing and a separate Cloudinary restriction approval are required before receipt protection is declared complete.

## Audit before implementation

Branch feat/customer-deletion-ledger starts at cdad4b1. No production connection or live deletion is authorized.

Customer account actions run in backend/routes/customer_security.py and services/customer_security.py. The old unfinished() reads order_status OR fulfillment_status OR status, so a stale order_placed hides a cancelled legacy status. It also fails to recognize closed/completed aliases. The cancellation approval handler synchronizes the three statuses but deliberately leaves paid refunds approved until settlement; approved is not proof of money returned. No actual affected production order was inspected, so stale fields are a code-level cause, not a diagnosis of a specific live record.

Archive is orders.is_deleted; restore clears it. The existing physical-delete endpoint always blocks because there is no safe test-order marker. Orders.items has delete-orphan cascade; physically deleting an order is inappropriate. Payment state/reference/receipt reside on orders; payment_approval_logs, cancellation_requests, invoice files and delivery records provide related history. Customer deletion currently preserves identifiable email to prevent email-owned history reassignment and returns only a generic unfinished-order error. User.profile/addresses have delete-orphan relationships: retain a pseudonymous user ID rather than deleting the User ORM object.

The improvement must distinguish cancelled unpaid orders from paid cancellations requiring a processed refund; protect active dispatch, pending/approved refunds, requests, unknown financial states and explicit retention holds. Normal customer results must hide deleted users. Original order IDs/amounts/items/payment references and financial/invoice history must remain reconcilable. This is operational removal and profile erasure, not destruction of legally retained accounting evidence.

## Implemented behavior

- Shared blockers consider all three lifecycle fields, pickup completion and legacy closed/completed aliases. Archived/soft-deleted orders still participate in customer eligibility checks. Unpaid cancellations can close; paid cancellations require a recorded processed refund. Approved/pending refunds, pending requests, unknown payment states/chargebacks, active dispatch/accepted assignments, unsettled completed-order collections and explicit holds block action. Historical delivered/cancelled assignment records do not constitute an active delivery. Historical payment approval prevents falsely treating a previously paid cancellation as unpaid, but cannot override a currently rejected payment for a completed order. No synthetic refund settlement is written.
- Blocked responses identify exact order ID/code and request IDs where available, with the required remedy. A rejection is recorded in the existing Admin Activity Log before returning 409. Success and activity entry commit together, including actor ID/role, timestamp, record ID, supplied reason, outcome and a non-sensitive summary. Email/phone patterns are redacted from new reasons; operators must not enter names or other personal data into free text. Existing audit history is not deleted.
- Archived Orders has a Super Admin-only Remove permanently button. Reason and exact `REMOVE ORDER <internal id>` confirmation are required on both client and server. Eligible rows are marked operational_removed_at; they remain is_deleted=true, disappear from normal and archived order results/search, and cannot be restored. No inventory restoration/deduction is performed by this action. The original Order and OrderItem rows, financial amounts, payment references, receipts/approval logs, cancellation/refund records and delivery history are retained. The existing physical-delete endpoint is not enabled or weakened.
- The same original orders form the historical ledger, not a duplicate accounting database. Super Admin-only `/admin/historical-orders` (50/page), `/admin/historical-orders/{id}` and `/admin/historical-orders/{id}/invoice` provide retained financial access. Invoice responses are no-store. Original PDFs are preserved without overwriting; if an original is missing the ledger endpoint does not regenerate it as original evidence. Before initial erasure/removal a missing current invoice can be generated while the full source record is still available. Private invoice paths are never exposed through static uploads. Normal invoice requests for erased identities require Super Admin access. Local retained receipt URLs are denied through static uploads; external receipt protection requires the gate below.
- Customer deletion retains only a pseudonymous, inactive internal User row for foreign-key/history reconciliation. Email becomes a random erased.invalid value; passwords are randomized, session_version increments, verification/recovery tokens are removed, push tokens cleared, and tracking capabilities revoked. Profile/contact/address/notes fields and account verification proof are cleared; saved addresses are removed after clearing order references. Orders are bound to the original customer internal ID and their customer email/contact/address copies are cleared. Cancellation request contact copies and customer notifications are cleared/removed. Original email may subsequently register a new account, which cannot claim old ID-linked orders. Deleted users are excluded from normal customer lists/search; only Super Admins may inspect their minimal internal detail record.
- User→orders lock order matches checkout's existing user lock. Order operations/removal lock the original rows. PostgreSQL triggers protect against stale legacy writers by rejecting changes to frozen order business data, inserts/updates to related payment/refund/offer records, changes/deletion of frozen order items, and checkout inserts for inactive/deleted accounts. Contact-only cancellation-request anonymization is allowed without changing financial evidence. Restoration and removal-marker reversal are rejected by the database. Guards do not run against unrelated active records. No PostgreSQL concurrency test has been executed here; isolated SQLite tests cover serial interleavings, and SQL/canonical-trigger verification tests cover the guard definitions.

## Additive migration plan — not executed

New script: backend/scripts/migrate_retained_orders.py. The already-authoritative migrate_customer_security.py is unchanged. This new migration adds only orders.operational_removed_at, personal_data_erased_at (nullable timestamps), retention_hold (nonnull false) and retention_hold_reason; installs three trigger functions and six triggers on existing tables. It creates no ledger/customer/payment tables, deletes no records, and does not backfill erased or removed states. It requires existing customer-security fields and existing order_items/cancellation_requests/payment_approval_logs/delivery_offers tables.

Default invocation is plan-only and does not connect. `--apply` and `--verify` are mutually exclusive explicit modes; verify is read-only. PostgreSQL application is one transaction, with a 5s lock timeout, 60s per-statement timeout and advisory migration lock. ALTER TABLE and trigger installation can block writers briefly, and deadlocks/serialization conflicts must cause rollback rather than bypassing guards. Rehearse on PostgreSQL 11+ with realistic staging data first. See [PostgreSQL row locking](https://www.postgresql.org/docs/current/explicit-locking.html) and [row trigger behavior](https://www.postgresql.org/docs/current/trigger-definition.html). There is no destructive down migration.

## Storage, privacy and financial retention gates

Render repository storage is not assumed durable. Before PostgreSQL actions can run, the operator must configure an approved absolute private persistent directory in RETAINED_INVOICE_STORAGE_DIR and attest RETAINED_INVOICE_STORAGE_DURABLE=true. The application does not provision a disk/provider, move old invoice files, change Render/Vercel settings or claim that the current production service has durable storage. Back up and checksum original PDFs before an approved copy to that private location; do not discard originals. Existing invoice paths are supported until that approved configuration, but destructive actions remain blocked.

Orders with receipt URLs or receipt-audit attachments also require RETAINED_PAYMENT_EVIDENCE_PROTECTED=true before PostgreSQL erasure/removal. Set this only after verifying private authorized access, durable retention and backups for the existing local/Cloudinary receipt assets. This flag is an operator attestation, not an automatic conversion of public CDN assets into private ones. No remote URLs are fetched, media deleted or provider configuration changed by this task. Without approved receipt protection, the blocker explicitly requires that protection first.

Immutable originals (invoice PDFs, bank receipts, financial references, refund evidence, delivery records and existing audit text) can contain personal data legitimately needed for financial/legal reconciliation. They are retained as evidence, not as identifiable login/email tombstones. The business must approve a documented purpose, access policy and finite legal retention/deletion schedule before rollout; this change does not invent a statutory period or supply an automatic purge of legal evidence. External avatar/media copies, previously sent emails, exports, backups, provider logs and free-text legacy records need the existing operator privacy/retention process. No claim of erasure from all external systems is made. The application profile and operational contact copies are erased immediately.

The schema previously had no dispute/legal-hold model. Existing disputed/unknown payment states are blocked, and Super Admins can register or release an explicit order hold at POST `/admin/orders/{id}/retention-hold?enabled=true|false` with a reason and `HOLD ORDER <id>` (setting) or `RELEASE HOLD ORDER <id>` (clearing) confirmation; both outcomes are audited. Review external disputes/holds before deletion. A paid nonrefundable cancellation cannot be declared settled merely by editing a reason: this implementation conservatively requires processed-refund evidence; separately reviewed financial-closure support would be needed for a legal non-refund settlement. Do not falsely mark refunds processed to bypass this restriction.

## Rollback

Before commit, PostgreSQL migration errors roll back schema/trigger changes. After commit, retain additive columns and triggers, ledger rows, audit records and original evidence. Never drop fields/guards, restore deleted profile PII from backups, reverse removal markers, restore session versions or cascade-delete history as a rollback. Customer erasure is intentionally irreversible.

Prefer a forward fix or a reviewed compatibility backend. Rolling back to old code that exposes /uploads/invoices or regenerates erased invoices can disclose/overwrite retained evidence: retain this private-file protection or block both static and invoice-regeneration paths at the approved proxy before rollback. Disable destructive UI/API actions and retain database guards when reverting frontend/application behavior. Old restore/payment/refund writers may receive guarded 409/500 responses; do not bypass guards to make them succeed. Historical corrections need a separately approved audited accounting workflow, not reopening a frozen operational record.
