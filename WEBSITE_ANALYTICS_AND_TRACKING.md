# Website analytics and secure order tracking

## Existing architecture reused

The audit found no GA4, Vercel Analytics or other visitor analytics script in the React/Vite source. Existing Admin reporting uses authoritative FastAPI/SQLAlchemy order aggregates, not visitor traffic; it remains unchanged. Website Analytics uses the existing Admin shell and `reports:view` permission. Customer tracking reuses `/orders`, its authenticated order details, existing PIN visibility, rider access rules, receipt upload, status mapping and polling cadence. Resend remains the only email sender. No mobile application files are changed.

## Required configuration (not applied to production)

1. Create/select a dedicated GA4 web property/stream. Enable the Google Analytics Data API in the service account's Google Cloud project. Grant that service account Viewer access to the GA4 property. No historical traffic is available unless this property already collected it.
2. Set `VITE_GA4_MEASUREMENT_ID=G-...` in Vercel and rebuild the frontend. This identifier is public, not a credential. No analytics script is loaded if it is missing/invalid or the visitor has not opted in.
3. Set Render-only `GA4_PROPERTY_ID` (numeric) and `GA4_SERVICE_ACCOUNT_JSON` (service account JSON via secure environment configuration, never a VITE variable). Reporting uses read-only OAuth scope. Default `GA4_REPORT_TIMEZONE=Africa/Lagos` must match the property's reporting timezone. Set it explicitly if the property uses a different timezone.
4. For purchases, set Render-only `GA4_MEASUREMENT_ID` to the same web stream, `GA4_API_SECRET` to its Measurement Protocol secret, and `GA4_PURCHASE_START_DATE=YYYY-MM-DD` to the approved collection launch date. Before enabling purchases, approve and run `python backend/scripts/migrate_website_analytics.py` from the repository root with the intended database environment. It only creates the `website_analytics_purchases` table. It never changes orders. The server returns `migration_required` if this table is absent.
5. For guest links, approve and run `python backend/scripts/migrate_order_tracking.py` with the intended database environment. It creates `order_tracking_tokens` and `order_tracking_limits` only. Set `ORDER_TRACKING_LINKS_ENABLED=true` after migration and verify existing `FRONTEND_URL` points to the HTTPS FoodNova domain and Resend email is enabled. No production migrations were run by this release. Missing tables/configuration do not break startup or owner tracking.
6. Deploy the backend on Render as well as the frontend on Vercel. Without the new backend routes, the UI displays unavailable states. Review privacy disclosures, processor arrangements and GA retention settings before enabling collection. Disable enhanced measurement, automatic page views/history tracking, Google signals, user-provided data and advertising features in the GA stream; this application sends only explicit allowlisted events. Do not add a duplicate GA/GTM/Vercel analytics script.

## Collection and accuracy boundaries

Register `purchase` as a GA4 key event. Conversion reporting uses the official `sessionKeyEventRate:purchase` metric (fraction converted to percent), not event-filtered session counts or truncated lists. If the property has not registered this key event, that metric remains unavailable while the other reports can still work.

Basic consent mode blocks Google loading until opt-in. Reject/withdraw and Global Privacy Control stop this integration; withdrawal clears accessible GA cookies. Preference storage lasts 180 days. No names, emails, phone numbers, addresses, user IDs, precise locations, free-text searches or URL query/fragment values are sent. Referrers are reduced to external origins. GA necessarily receives browser network requests and reports approximate location/device aggregates; the application does not store visitor IPs or show individual visitor identities. There is no customer-profile/browsing-history join.

Events: `page_view` for allowlisted public pages and SPA navigation, `view_item` for product/pack details, `search` with the constant safe label “catalogue search”, `add_to_cart` after the existing cart adds items, `begin_checkout` when entering checkout with items, and backend `purchase`. Page/detail/checkout render duplicates are suppressed. New browser checkout orders use the existing `order_source` column with `customer_web`; older/native clients retain `customer_app`, and the public schema rejects Admin source values. Only `customer_web` orders qualify for website purchase reporting, preventing manual/native orders from inflating website conversions. This changes origin metadata only, not payment, price or inventory rules. Free-text queries and campaign query parameters are intentionally omitted, so acquisition may be less detailed than a marketing attribution system.

Purchases are not emitted on checkout creation, receipt submission, callbacks or webhooks. A consenting signed-in customer revisiting the existing My Orders flow supplies only GA client/session identifiers transiently to an owner-authorized endpoint. The server reloads the order, checks the existing confirmed-payment statuses, rejects cancelled/refunded/deleted and pre-launch orders, and builds value/items from stored order records. A unique durable order claim and stable transaction ID prevent repeat submissions across refreshes/devices/workers. No client/session ID is persisted in the ledger. Ambiguous network failures are marked `uncertain` and never automatically retried, favouring undercounting over duplicates. HTTP acceptance is not proof of GA processing. Purchases confirmed offline without a later consenting visit are not collected; attribution is to that later GA session. Refund/cancellation reversals are not sent to GA: use financial reports for net revenue. No payment/order/inventory timing changes were made.

Reporting caches bounded aggregate results for five minutes per property/range/report set. Totals come from GA aggregate requests, never from truncated top lists or paginated business orders. The dashboard summary requests only four required reports. Tables show top rows and flag truncation, sampling, thresholding and high-cardinality loss. Data may be delayed 24–48 hours and is consent-dependent/estimated. Conversion rate is sessions with a purchase divided by total sessions in the same range, not purchases divided by visitors. Funnel rows are independent event counts, not a sequential/cohort funnel. Not configured/unavailable differs from a successfully empty report (genuine zero).

## Secure tracking

`POST /tracking/lookup` accepts an order number and optional email. An authenticated customer's email must match the order under existing ownership rules for private details. Otherwise the response is neutral for unknown, non-owned and known orders; order numbers alone reveal no status. A matching email causes a link to be sent only to the order's stored address, under shared database-backed per-IP and per-order/email limits. Invalid formats are rejected. Rates use HMAC identifiers and short retention, never raw email/IP records. By default, abuse limits use the socket peer and ignore spoofable forwarding headers. Before enabling links behind Render's proxy, configure `ORDER_TRACKING_TRUSTED_PROXIES` with verified direct-proxy CIDRs and verify that the proxy appends the true client IP as the last X-Forwarded-For entry. Otherwise visitors behind the same proxy share a conservative limit; never configure all internet addresses as trusted.

Capabilities use 32 random bytes, SHA-256 hashes at rest, 30-day expiry, order binding and revocation via the Admin-only `POST /tracking/{order_id}/revoke-links` endpoint (`orders:update`). `POST /tracking/progress` returns only general fulfilment status and pickup/delivery method. It never returns order identifiers, identity, products, totals, payment details, riders, GPS or PINs. Responses use no-store/private and no-referrer policies. Tokens travel in POST bodies, never endpoint URLs. Email URLs use `/orders#track=...`; the provider immediately strips the fragment and holds the capability in memory only. No analytics event includes it, and HTML sets no-referrer globally. Reload after stripping requires reopening the email or requesting another link.

The existing order-placed email gets one secure CTA when guest tracking is enabled; it does not send a second confirmation or change triggers. Failure/configuration fallback preserves the existing My Orders link. Token-bearing email failures log error types only. Older orders can request a new link through the verified email flow; no bulk token backfill or per-request regeneration occurs. Repeated confirmation retries may issue a new short-lived capability; all can be revoked together. Expired token rows can be purged by approved maintenance after expiry.

The floating widget sits above cart/back-to-top controls, is hidden in Admin/checkout/cart/full tracking routes and while the consent panel is open. The dialog supports Escape, focus trapping/restoration and scroll locking. The existing `/orders` route hosts the same limited view for guests and retains the full owner page. Polling runs every 20 seconds only while an open dialog/full tracking view is active, pauses hidden tabs, waits for requests, cancels on cleanup, and stops on terminal states. Timelines show lifecycle progression, not invented timestamps or ETAs.

## Validation and release limits

Disable email-provider click tracking for capability-bearing links; the approved mail provider necessarily receives the email body, but raw capabilities should not be copied into click-tracking/analytics services.

Automated suites cover consent, event redaction/deduplication, owner authorization, paid-purchase rules, durable claims, date ranges, empty/failing reports, token expiry/revocation, guest redaction, neutral lookup, email CTA and rate limits. Existing payment/PIN/inventory/dispatch regressions must also pass before release. Browser tooling previously failed to connect; responsive CSS/source contracts and HTTP/asset checks are not substitutes for actual desktop/mobile screenshots, runtime console checks or authenticated production acceptance. Real GA reports/events cannot be verified without property configuration and consent; no historical figures are claimed.

Official implementation references: [GA4 Data API](https://developers.google.com/analytics/devguides/reporting/data/v1/rest/v1beta/properties/runReport), [basic consent mode](https://developers.google.com/tag-platform/security/guides/consent?consentmode=basic), [Measurement Protocol](https://developers.google.com/analytics/devguides/collection/protocol/ga4/reference).
