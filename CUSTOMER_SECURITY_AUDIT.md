# Customer experience and security: audit before implementation

Baseline: production `main` / `origin/main` at `512a76c0223c9ab8cf8ab08a9fbf143da8b88b94` (fetch verified, no divergence). Work is isolated on `feat/customer-security-tracking`. Existing untracked attachments, worktrees, release notes and mobile screenshots are preserved. Nothing will be pushed to main or deployed automatically.

## Active backend implementation

- `backend/main.py` constructs FastAPI (`fastapi_app`) and wraps it with Socket.IO when configured. It registers the active monolithic routes and includes the newer `routes/order_tracking.py` and `routes/website_analytics.py`. Older `backend/auth.py` and `routes/admin.py` are not substitutes for auditing these handlers.
- Registration: `POST /auth/register`, with `/api/auth/register` and `/register` compatibility wrappers forwarding to it. Login: `POST /auth/login`, `/api/auth/login`, `/login`. Admin and delivery-worker login handlers are separate and must remain unchanged. Password recovery uses `/auth/password-reset/request` and `/auth/password-reset/confirm`.
- `models.User` is the authoritative customer/admin identity store. It already has `is_active` and `session_version`; JWT creation and `_get_user_from_token` validate both on every authenticated request. No customer verification field, verification token lifecycle, or suspend/deactivate/delete management API exists.
- Registration creates a customer, profile and usable JWT immediately. Login permits active customers without email verification. All registration aliases must receive the same verification behavior; recovery and verification must remain possible for unverified active customers.
- Orders use `models.Order` / OrderItem, `POST /orders` (also `/api/orders`), `/orders/my`, `/orders/{id}`, invoices and rider-location routes. Creation uses the existing inventory transaction and delivery-zone validator. Customer ownership currently relies on matching the authenticated email; customer_user_id already exists and should be populated for new orders. Checkout currently has no verified-email gate.
- Admin customer listing is the active `GET /admin/customers` in main, authorized by customers:view or orders:manual_create. It loads all customers and their profiles/addresses/orders without server pagination. Password-reset and export routes already exist. No lifecycle management should be built in the unused legacy admin router.
- `email_service.py` is the Resend integration, including order confirmations, fulfillment PINs, password recovery and secure tracking CTA. Token-bearing error logging is already sanitized. Extend this service rather than creating another sender.
- Guest tracking already uses hashed random, expiring/revocable capabilities, database-backed HMAC abuse limits, no-store responses and strict progress redaction. Activation still requires the previously documented tracking migration/configuration. Reuse `/tracking/lookup` and `/tracking/progress`; do not weaken guest verification or create another order database.

## Active frontend implementation

- React/Vite routes are in `src/App.jsx`. `/orders` currently combines the full customer order page with guest tracking entry. `OrderTrackingProvider` consumes fragment capabilities, scopes private results to the current identity and polls only when active. The floating widget currently hosts a modal; change it to a `/track-order` shortcut while retaining compatibility for old email links.
- Auth uses Zustand `authStore`, bearer tokens and existing API interceptors. Cart is a separate persisted Zustand store; auth changes do not need to clear it. Registration always redirects home; login currently accepts only an Orders return target. Checkout currently renders its order form for unauthenticated users and only discovers authorization failure on submission.
- AdminCustomers currently searches client-side and can fall back to customers inferred from orders. That fallback is unsuitable for account-state management or complete pagination. The upgraded screen must use authoritative customer records and clearly fail if unavailable.

## Implementation and transition decisions

Follow-up live-connection audit found that Socket.IO connect used signature-only decode and order:subscribe joined an arbitrary order room without ownership verification. The branch must use the same database-backed token/session-version checks as REST, authorize order subscriptions, and prevent revoked sockets from receiving subsequent emissions. No new WebSocket service or broker is introduced.

Add customer status, verification timestamp, single-use hashed verification tokens and checkout idempotency through an explicit additive migration. Reuse session_version for immediate revocation. Super Admin lifecycle actions require a reason and typed confirmation, audit in the same transaction, lock the customer row and block deletion with unfinished orders/refunds. Account deletion will be a non-login tombstone, not SQL deletion: retain its unique email as a protected historical identity reservation (preventing email reuse from claiming old email-owned orders), clear profile/contact/address display data, and retain financial/order/invoice/delivery history. This is retention, not a claim of complete erasure; operator retention policy review is required before deployment.

Existing accounts will not be falsely marked verified. They may log in to verify/recover; enable `CUSTOMER_EMAIL_VERIFICATION_REQUIRED=true` only after migration, Resend verification and a customer notice/resend transition period. Once enabled, every unverified customer is blocked from customer order creation. New registrations receive verification emails immediately. No production migration, environment change, push to main or deployment is authorized in this task.

New registrations are individually verification-required immediately, even during the legacy grace period. The global switch ends grace for older accounts. The existing unique order idempotency column is reused; only the request-hash column is additive for checkout. Browser drafts are scoped to their customer identity on re-authentication, and signing into a different account clears a prior account's draft.

Checkout will keep delivery drafts in session-only memory across connected login/register routes (no new persistent storage of addresses), preserve the existing persisted cart, use an allowlisted return route, and revalidate current account status on the server. A customer-scoped idempotency key will protect retries from duplicate orders without changing inventory/payment timing.
